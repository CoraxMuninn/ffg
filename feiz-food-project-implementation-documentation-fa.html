02 پروژه چه چیزی قرار بود باشد؟

پروژه Feiz Food Group صرفاً یک وب‌سایت شرکتی نبود؛ با رویکرد Business Operating System Foundation طراحی شد — یعنی یک پلتفرم B2B صادراتی که به‌عنوان پایه عملیات تجاری عمل کند، نه یک صفحه‌ی نمایشی. هر بخش به‌جای «دکوراسیون»، یک قابلیت عملیاتی برای یک صادرکننده بین‌المللی طیور منجمد است.

۱. جذب خریداران خارجی

بدون حضور بین‌المللی، هیچ خریدار خارجی شرکت را پیدا نمی‌کند. وب‌سایت چندزبانه + SEO، کانال اصلی جذب بود.

۲. ایجاد اعتبار بین‌المللی

خریدار B2B پیش از معامله، اعتبار تأمین‌کننده را بررسی می‌کند؛ گواهینامه‌ها، کیفیت و زنجیره تأمین، پایه اعتمادند.

۳. مسیر حرفه‌ای Buyer Journey

مسیر «خانه → محصولات → جزئیات → اعتماد → بازارها → RFQ» باعث می‌شود خریدار با اطمینان به درخواست قیمت برسد.

۴. نمایش محصولات

محصولات (پاچک/پای مرغ + ۳ محصول ثانویه) باید مشخصات واقعی را شفاف نشان دهند؛ مشخصات مهم‌ترین عامل مقایسه است.

۵. نمایش کنترل کیفیت

فرآیند QC مستند، به خریدار نشان می‌دهد محصول با استاندارد مشخص و قابل‌بازرسی تحویل می‌شود.

۶. نمایش زنجیره تأمین

نشان دادن ۹ مرحله زنجیره سرد، قابلیت لجستیکی صادرکننده را اثبات می‌کند.

۷. مسیر RFQ

تبدیل اصلی کسب‌وکار «درخواست قیمت» است؛ فرم + API + ایمیل، درخواست را به تیم فروش می‌رساند.

۸. زیرساخت SEO بین‌المللی

متادیتا، hreflang، sitemap، robots و JSON-LD برای دیده‌شدن در بازارهای هدف ضروری‌اند.

۹. معماری چندزبانه

۴ زبان (انگلیسی، فارسی، روسی، ویتنامی) برای بازارهای هدف؛ ویتنام به‌عنوان بازار اصلی اولویت دارد.

۱۰. زیرساخت CMS

محتوای CMS-driven (Decap CMS → GitHub → Markdown) به تیم غیرفنی اجازه می‌دهد محتوا را بدون کد مدیریت کند.

04 قوانین پروژه و Master Specification

یک Master Project Specification به‌عنوان منبع حقیقت پروژه ایجاد شد تا تمام تصمیم‌ها را کنترل کند. این سند نقش حیاتی در جلوگیری از مشکلات زیر داشت:

Scope Drift

با تعریف دقیق صفحات، محصولات، بازارها و زبان‌ها، پروژه از مسیر خارج نشد.

Feature Creep

هر قابلیت باید مستند می‌بود؛ افزودن ویژگی بی‌دلیل ممنوع شد.

Fabricated Claims

قانون سخت: هیچ MOQ، قیمت، ظرفیت، مشتری یا گواهی ساختگی.

Design Inconsistency

Design System یکپارچه (Navy/Cyan/Smoke) از پراکندگی بصری جلوگیری کرد.

Technical Inconsistency

قواعد پشته فنی (Server Components، بدون DB، بدون Base UI/Radix) یکنواختی معماری را حفظ کرد.

نتیجه: تمام تصمیمات تأییدشده در این سند مرجع، به‌عنوان «قفل‌شده» در نظر گرفته شدند و در تمام مراحل رعایت شدند.

07 معماری RTL / فارسی

RTL صرفاً ترجمه متن به فارسی نبود؛ یک معماری مستقل برای جهت‌دهی راست‌به‌چپ بود:

  • dir="rtl" در سطح سند (html) — نه کامپوننت‌ها.
  • Vazirmatn برای متن فارسی؛ Inter برای زبان‌های LTR.
  • icon direction — آیکون‌های جهت‌دار (فلش‌ها) در RTL با rtl:rotate-180 می‌چرخند.
  • navigation / mobile menu / forms / spacing با ویژگی‌های منطقی CSS (ms/ps/start/end).
  • language switcher با Escape و مدیریت فوکوس، مستقل از جهت.
  • accessibility — فوکوس، skip link و RTL سازگار.
تصحیح اصطلاح فارسی: در تمام محتوای فارسی، عبارت «پاچک مرغ» به «پای مرغ» اصلاح شد.

09 Responsive و Mobile UX

Mobile-first به‌دلیل اینکه بخش بزرگی از خریداران B2B از موبایل بازدید می‌کنند انتخاب شد. تجربه موبایل باید حس یک Modern Mobile App داشته باشد، نه فشرده‌سازی دسکتاپ.

  • touch targets بزرگ (دکمه‌های ≥44px)
  • منوی موبایل تمام‌صفحه با RTL
  • چیدمان‌های responsive و stacking
  • قرارگیری CTA مناسب موبایل
  • فرم‌ها و language switcher سازگار با لم
  • انیمیشن سبک + reduced motion
  • دسترس‌پذیری و فوکوس در موبایل
همه این موارد از نظر فنی پیاده و تأیید محلی شده‌اند؛ حس نهایی روی دستگاه واقعی نیازمند Human QA است.

12 معماری محصولات

Primary — Frozen Chicken Feet

محصول اصلی صادراتی؛ عمیق‌ترین ارائه با مشخصات کامل (Grade A/A+، IQF، 35–55g، گلیز ۵–۱۰٪، -18°C).

Secondary — Liver / Gizzard / Heart

عمداً با جزئیات کمتر ساخته شدند؛ چون مشخصات مستند ثانویه محدود بود و افزودن مشخصات ساختگی ممنوع است.

  • Dynamic routes: /[locale]/products/[slug] — یک قالب مشترک برای هر ۴ محصول.
  • CMS-driven content: تمام مشخصات از Markdown می‌آید.
  • localized content: محصولات در هر ۴ زبان.
  • specs + CTA + RFQ + JSON-LD + SEO: برای هر محصول.

13 سیستم جزئیات محصول

صفحه جزئیات محصول شامل: مرور کلی، مشخصات، اطلاعات خریدار، تصویر، CTA به RFQ، structured data (Product + Breadcrumb) و localization است.

خودداری عمدی از ادعاهای اطلاعاتی: هیچ MOQ، قیمت، ظرفیت، زمان تحویل، نام مشتری یا گواهینامه بی‌پشتوانه درج نشد. دلیل: قانون سخت پروژه — هر ادعا باید توسط مستندات پشتیبانی شود. این «نقص» نیست؛ یک تصمیم صحیح و مستند است.

14 کنترل کیفیت

صفحه کنترل کیفیت برای B2B حیاتی است؛ زیرا خریدار بین‌المللی پیش از خرید، قابلیت QC تأمین‌کننده را ارزیابی می‌کند. ۹ فرآیند مستند: تأیید نمونه، کنترل دما، آزمایش گلیز، یکنواختی اندازه، بازرسی نسبت قطعات شکسته، تست بوی پس از یخ‌زدایی، بازرسی تصادفی کارتن، عکس مهر و موم کانتینر، بازرسی پیش از بارگیری.

ارتباط با Trust Building: هر فرآیند یک «شاهد» از کنترل واقعی است و به خریدار اطمینان می‌دهد محصول با استاندارد مشخص و قابل‌بازرسی تحویل می‌شود.

15 زنجیره تأمین

صفحه زنجیره تأمین ۹ مرحله را نمایش می‌دهد: مزرعه، فرآوری، درجه‌بندی، انجماد IQF، انبار سرد، بازرسی کیفیت، بارگیری کانتینر، حمل دریایی و تحویل در مقصد (Destination Delivery).

نشان دادن کل زنجیره سرد برای یک صادرکننده، توانایی لجستیکی و تعهد به -18°C را از مزرعه تا مقصد اثبات می‌کند.

16 گواهینامه‌ها و اعتماد

Certifications (۶ گواهی)

HACCP، ISO 22000، حلال، گواهی بهداشت، گواهی دامپزشکی، گواهی مبدأ — حل نیاز به اثبات انطباق.

Trust / Capability Features (۸ قابلیت)

تأمین مطمئن، QC سخت‌گیرانه، یکپارچگی زنجیره سرد، صادرات عمده، اسناد صادراتی، برچسب اختصاصی، بازرسی پیش از بارگیری، همکاری بلندمدت — حل نیاز به اعتماد به توان عملیاتی.

چرا نباید گواهینامه یا ادعای ساختگی ایجاد کرد؟ چون این کار اعتبار واقعی و مسئولیت‌پذیری را از بین می‌برد و در بازار B2B، دروغ به‌سرعت افشا می‌شود.

17 بازارها

یک صفحه بازار واحد: ویتنام (اصلی) + امارات، روسیه، تایلند (ثانویه). به‌دلیل مشخصات، برای هر کشور route جداگانه ساخته نشد — سند صراحتاً یک صفحه بازار را تعیین کرده بود.

ثبت شفاف: توضیحات بازارها عمداً مختصر نگه داشته شدند تا از ادعاهای بی‌پشتوانه جلوگیری شود. این یک تصمیم عمدی است، نه «thin content» به‌معنای نقص.

18 سیستم بلاگ

۶ مقاله در ۳ ستون محتوایی:

  • Product: «چه چیزی را هنگام تأمین پای مرغ منجمد بررسی کنیم»، «IQF در برابر بلوکی».
  • Quality / Cold Chain: «زنجیره سرد — واردکننده چه چیزی را تأیید کند»، «کنترل کیفیت برای خریداران».
  • International Trade: «تأمین بین‌المللی»، «رابطه تأمین مطمئن».

هر مقاله: لینک داخلی، متادیتا، Article schema، تصویر، و محتوای بومی‌شده در ۴ زبان. نقش بلاگ در SEO، Trust، Buyer Education و Organic Acquisition.

21 امنیت و سخت‌سازی

Timeline مشکلات پیدا و رفع‌شده

HIGH — Origin validation weakness

هر origin HTTPS پذیرفته می‌شد → رفع: فقط hostname واقعی + localhost + https.

تست: evil/attacker/missing → 403. VERIFIED

HIGH — CRLF / Email Header Injection

کاراکترهای CR/LF در subject و body → رفع: حذف تمام control chars در sanitize + دفاع عمیق subject.

تست: بدون CRLF و Bcc پس از رفع. VERIFIED

HIGH — X-Forwarded-For Rate Limit Bypass

spoofing XFF برای دور زدن rate limit → رفع: گیت TRUST_PROXY؛ بدون proxy از کلید پایدار استفاده می‌شود.

تست: ۶ درخواست spoofed → 429. VERIFIED

MEDIUM — JSON-LD `</script>` Injection

بریک‌اوت script در JSON-LD → رفع: escape کردن `<`/`>`/`&`.

تست: بدون `</script>` خام؛ JSON معتبر. VERIFIED

LOW — Content-Type false positive

substring `application/jsonp` پذیرفته می‌شد → رفع: matching دقیق media type. VERIFIED

LOW — Server Config in Client Component

RFQ config وارد Client bundle می‌شد → رفع: فقط site key عمومی از Server Component ارسال می‌شود.

تست: بدون secret در bundle. VERIFIED
