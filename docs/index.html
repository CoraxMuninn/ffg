📌 قوانین کلیدی چندزبانه

  • Slug انگلیسی ثابت برای همه زبان‌ها: /fa/products/frozen-chicken-feet
  • x-default → English (سئوی بین‌المللی)
  • RTL/LTR در سطح <html dir> — نه در سطح کامپوننت
  • Logical CSS properties (margin-inline, padding-block) برای سازگاری RTL
  • ترجمه ماشینی بی‌کیفیت به‌عنوان محتوای نهایی منتشر نمی‌شود

استراتژی میزبانی تصاویر و رسانه‌ها

با حدود ۳۰ تا ۴۰ تصویر در کل پروژه، ساده‌ترین و امن‌ترین راه‌حل، ذخیره مستقیم در GitHub Repository است.

📸 استراتژی سه‌مرحله‌ای: GitHub Repo → Cloudflare R2 → Cloudinary
🏆

مرحله ۱ — GitHub Repo (اکنون)

وضعیت: انتخاب نهایی ✅
تصاویر در public/media/ ذخیره می‌شوند. Decap CMS مستقیماً پشتیبانی می‌کند. ~۲۰MB برای ۴۰ تصویر = هیچ تأثیری بر repo. نسخه‌بندی با Git. بدون هزینه. بدون dependency اضافی.

☁️

مرحله ۲ — Cloudflare R2 (آینده)

وضعیت: اگر نیاز شد
۱۰GB رایگان + CDN جهانی. بدون egress fee. S3-compatible. مناسب وقتی تعداد تصاویر یا ترافیک بالا رفت. مهاجرت آسان با URL redirect.

🖼️

مرحله ۳ — Cloudinary (اختیاری)

وضعیت: فقط در صورت نیاز خاص
بهینه‌سازی خودکار (WebP/AVIF, resize). URL-based transformations. فقط اگر بهینه‌سازی real-time لازم شد.

📁 ساختار پوشه تصاویر در Repository

  • public/media/logo/ — لوگوی Feiz Food (SVG + PNG)
  • public/media/hero/ — تصاویر Hero Section ( Reefer containers, cargo ship, cold storage )
  • public/media/products/ — تصاویر محصولات (Chicken Feet, Liver, Gizzard, Heart)
  • public/media/certifications/ — لوگوی گواهینامه‌ها (HACCP, ISO, Halal...)
  • public/media/supply-chain/ — تصاویر زنجیره تأمین (Farm, IQF, Cold Storage, Shipping)
  • public/media/quality/ — تصاویر کنترل کیفیت (Inspection, Lab, Packaging)
  • public/media/blog/ — تصاویر مقالات بلاگ

⚙️ تنظیم Decap CMS برای ذخیره تصاویر

  • media_folder: "public/media" — محل ذخیره فیزیکی تصاویر
  • public_folder: "/media" — URL عمومی تصاویر در سایت
  • فرمت پیشنهادی: WebP برای عکس‌ها — SVG برای لوگو و آیکون‌ها
  • حداکثر عرض: ۱۹۲۰px برای Hero — ۸۰۰px برای Product Cards
  • next/image به‌صورت خودکار resize، lazy-load و format conversion انجام می‌دهد
✅

چرا GitHub Repo؟

Decap CMS Native: بدون plugin یا custom widget.
Atomic Deploy: تصویر + Markdown همیشه با هم منتشر می‌شوند.
Version Control: هر تصویر تاریخچه تغییرات دارد.
Zero Cost: بدون سرویس اضافی.
No Vendor Lock: مهاجرت آسان در آینده.

❌

چرا UploadThing نه؟

طراحی برای User Uploads: نه CMS admin media management.
بدون Decap CMS Plugin: نیاز به custom widget.
۲GB رایگان: خیلی محدود.
هزینه بالا: $۲۰/ماه برای ۳۰GB — برای ۴۰ تصویر غیرضروری.
Over-engineering: پیچیدگی بدون نیاز واقعی.

📐 قوانین بهینه‌سازی تصاویر

  • Hero Images: ۱۹۲۰×۱۰۸۰ — WebP — priority loading — حداکثر ۲۰۰KB
  • Product Cards: ۸۰۰×۶۰۰ — WebP — lazy loading — حداکثر ۱۰۰KB
  • Certification Logos: SVG (بدون محدودیت حجم) — بدون lazy loading
  • Blog Images: ۱۲۰۰×۶۳۰ — WebP — lazy loading — حداکثر ۱۵۰KB
  • alt text: اجباری برای تمام تصاویر — توصیفی و SEO-friendly
  • ابزار فشرده‌سازی: squoosh.app یا sharp (CLI) قبل از commit

معماری امنیتی ۵ لایه

دفاع در عمق (Defense in Depth) — هر لایه تهدیدات خاصی را خنثی می‌کند. اگر یک لایه شکست بخورد، لایه بعدی محافظت می‌کند.

🛡️ معماری امنیتی ۵ لایه — از CDN/WAF تا محافظت داده‌ها
☁️

لایه ۱ — CDN / WAF (Cloudflare)

DDoS Protection: جذب حملات حجمی قبل از رسیدن به سرور. WAF Rules: مسدودسازی SQLi، XSS، Path Traversal. Bot Management: تشخیص و مسدودسازی بات‌های مخرب. SSL/TLS: رمزنگاری لایه انتقال.

🧱

لایه ۲ — شبکه (Reverse Proxy)

HTTPS اجباری + HSTS: هیچ ارتباط plaintext. Security Headers: X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy. IP Whitelist: محدودسازی دسترسی /admin. Rate Limiting: در سطح Nginx/Caddy.

🔧

لایه ۳ — اپلیکیشن (Next.js)

CSP: Content Security Policy سفارشی — فقط منابع مجاز. Server-side Validation: تمام ورودی‌ها سمت سرور اعتبارسنجی. Input Sanitization: پاکسازی XSS. Anti-bot: Honeypot fields + Challenge.

🔑

لایه ۴ — API Security

Rate Limiting (RFQ): حداکثر ۵ درخواست در ساعت per IP. CSRF Protection: توکن‌های یکبار مصرف. Safe Error Responses: بدون stack trace. Request Size Limit: جلوگیری از payload attacks.

🗄️

لایه ۵ — محافظت داده‌ها

Environment Secrets: تمام API keys فقط در process.env سمت سرور. No Client Exposure: هیچ secret به browser ارسال نمی‌شود. Encrypted Backups: بکاپ رمزنگاری‌شده. Dependency Audit: بررسی خودکار آسیب‌پذیری‌ها.

📋

لایه ۶ — مانیتورینگ و لاگ

Safe Logging: لاگ درخواست‌های مشکوک بدون افشای داده حساس. Audit Trail: Git history برای تمام تغییرات CMS. Error Tracking: Sentry یا مشابه (بدون stack trace به کاربر). Uptime Monitoring: هشدار فوری در صورت قطعی.

🔴 الزامات امنیتی بحرانی (Non-Negotiable)

  • Resend API Key — هرگز نباید به client-side JavaScript دسترسی داشته باشد
  • GitHub OAuth Token — فقط در Decap CMS backend flow استفاده شود
  • Environment Variables — فایل .env هرگز commit نشود (.gitignore)
  • Security Headers — باید در تمام responses وجود داشته باشند (تست: securityheaders.com)
  • HSTS — max-age حداقل ۳۱۵۳۶۰۰۰ (یک سال) + includeSubDomains
  • CSP — بدون unsafe-inline و unsafe-eval در production
  • VPS SSH — فقط key-based auth، بدون password، پورت غیر استاندارد

کنترل دسترسی ادمین

معماری احراز هویت و مجوزدهی برای Decap CMS — از درخواست دسترسی تا مدیریت محتوا با Editorial Workflow.

🔐 جریان احراز هویت ادمین — از IP Whitelist تا Editorial Workflow
1

IP Whitelist (سطح Nginx)

فقط IP‌های مجاز (دفتر شرکت + ادمین‌های مشخص) می‌توانند به مسیر /admin دسترسی داشته باشند. تمام IP‌های دیگر 403 Forbidden دریافت می‌کنند — حتی صفحه لاگین را نمی‌بینند.

دفاع لایه اول — مخفی‌سازی ورودی
2

GitHub OAuth (احراز هویت)

ادمین از طریق حساب GitHub خود وارد می‌شود. GitHub App مخصوص پروژه فقط به اعضای تیم اجازه ورود می‌دهد. احراز هویت بدون پسورد — از زیرساخت امن GitHub استفاده می‌شود.

بدون مدیریت پسورد — امنیت GitHub
3

2FA اجباری (GitHub Account)

تمام حساب‌های GitHub تیم باید Two-Factor Authentication فعال داشته باشند. بدون 2FA = بدون دسترسی به CMS. این الزام از طریق GitHub Organization Policy اعمال می‌شود.

اجباری — بدون استثنا
4

GitHub Permissions (RBAC)

دسترسی‌ها از طریق GitHub Repository Permissions مدیریت می‌شوند:
Admin: دسترسی کامل (Admin + Push + Merge)
Editor: فقط Editorial Workflow (Draft → Review) — بدون merge مستقیم
Viewer: فقط خواندن (Read-only)

نقش‌ها از GitHub ارث‌بری می‌شوند
5

Editorial Workflow (بازبینی محتوا)

Decap CMS از Editorial Workflow پشتیبانی می‌کند. هر تغییر ابتدا به یک Git Branch می‌رود، بعد از بازبینی merge می‌شود. مراحل: Draft → In Review → Ready → Published. هیچ محتوایی بدون بازبینی منتشر نمی‌شود.

کنترل کیفیت محتوا قبل از انتشار
6

Git Audit Trail (ردپای تغییرات)

هر تغییر در CMS = یک Git Commit با: نام کاربر، تاریخ/ساعت، diff تغییرات. تاریخچه کامل و قابل بازبینی. امکان Revert هر تغییر از طریق Git. بدون دیتابیس = بدون نگرانی از hand-tampering.

شفافیت کامل — هر تغییر قابل ردیابی
✅

مزایای این معماری

بدون دیتابیس احراز هویت = بدون سطح حمله SQL. بدون پسورد = بدون Brute-force. Git audit trail = تاریخچه تغییرات کامل. IP whitelist = مخفی‌سازی ورودی. GitHub 2FA = احراز هویت قوی.

⚠️

ریسک‌ها و راه‌حل‌ها

ریسک: GitHub outage = CMS غیرقابل دسترسی. راه‌حل: Markdown فایل‌ها مستقیماً قابل ویرایش از طریق Git CLI. ریسک: GitHub account compromise. راه‌حل: 2FA اجباری + IP whitelist.

مدل تهدید و دفاع

۸ تهدید اصلی که یک وب‌سایت B2B صادراتی با آن‌ها مواجه است و مکانیزم دفاعی هر یک.

⚠️ ۸ تهدید اصلی و مکانیزم‌های دفاعی متناظر
🌊

۱. DDoS Attack

تهدید: سیل درخواست‌ها برای از کار انداختن سرور.
دفاع: Cloudflare (لایه ۱) — جذب و فیلتر ترافیک مخرب قبل از رسیدن به سرور. Rate Limiting در Nginx (لایه ۲).

💉

۲. SQL Injection

تهدید: تزریق کد SQL مخرب.
دفاع: هیچ دیتابیسی وجود ندارد! Git-based CMS = بدون سطح حمله SQL. معماری ذاتاً مصون.

📜

۳. Cross-Site Scripting (XSS)

تهدید: تزریق JavaScript مخرب.
دفاع: CSP بدون unsafe-inline/eval (لایه ۳). React auto-escaping. Input sanitization سمت سرور. WAF rules (لایه ۱).

🔨

۴. Brute Force

تهدید: حدس زدن رمز عبور با تلاش مکرر.
دفاع: GitHub OAuth = بدون پسورد محلی. IP Whitelist = مخفی‌سازی ورودی. 2FA = لایه اضافی. Rate Limiting = مسدودسازی تلاش‌های مکرر.

🔄

۵. CSRF (Cross-Site Request Forgery)

تهدید: اجرای درخواست جعلی از طرف کاربر.
دفاع: CSRF Tokens برای فرم RFQ. SameSite cookie attribute. Origin/Referer header validation. Next.js built-in protections.

🔓

۶. Data Exposure

تهدید: نشت اطلاعات حساس (API keys, secrets).
دفاع: تمام secrets فقط در process.env سمت سرور. Server Components = هیچ داده حساسی به browser ارسال نمی‌شود. .env در .gitignore.

🤖

۷. Bot Spam (فرم RFQ)

تهدید: ارسال خودکار هزاران فرم جعلی.
دفاع: Honeypot field (مخفی از انسان). Cloudflare Bot Management. Rate Limiting (۵/ساعت). Turnstile challenge (بدون CAPTCHA آزاردهنده).

🕵️

۸. Man-in-the-Middle

تهدید: شنود ارتباطات بین کاربر و سرور.
دفاع: HTTPS اجباری + HSTS (یک سال). Cloudflare SSL/TLS. Perfect Forward Secrecy. Certificate auto-renewal.

🎯 Security Headers Checklist (Production)

  • Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  • Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:;
  • X-Content-Type-Options: nosniff
  • X-Frame-Options: DENY
  • Referrer-Policy: strict-origin-when-cross-origin
  • Permissions-Policy: camera=(), microphone=(), geolocation=()
  • X-XSS-Protection: 0 (غیرفعال — CSP کافی است)
  • Cross-Origin-Opener-Policy: same-origin

🔧 VPS Hardening Checklist

  • SSH: key-only authentication، پورت غیر استاندارد، fail2ban
  • Firewall: UFW/iptables — فقط پورت‌های 80, 443, SSH باز
  • Auto-updates: unattended-upgrades برای security patches
  • Node.js: اجرای اپلیکیشن با user غیر root (pm2 یا systemd)
  • Backups: روزانه خودکار + offsite storage + رمزنگاری
  • Monitoring: Uptime robot + log monitoring + alerting
  • Secrets: مدیریت از طریق environment variables (نه فایل hardcoded)
  • Rollback: Git-based deployment = بازگشت فوری به نسخه قبلی
